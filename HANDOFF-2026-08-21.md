## The three failure layers we walked through

The user's original request was: "help mail-archiver — Sync now failing for
Shreya on pnas-omv5s + vaman on pnas-omv12s." We uncovered three stacked
regressions/bugs. Layers 1 + 2 are FIXED. Layer 3 is DIAGNOSED, code fix
identified, NOT yet applied.

### Layer 1 — 1.1.0 systemd-run polkit regression (FIXED in 1.1.1)

- **Symptom:** WebUI Sync-now → `Failed to start transient scope unit:
  Interactive authentication required` (pnas-omv5s, polkit-installed) or
  `Access denied` (pnas-omv12s, polkit-absent).
- **Root cause:** 1.1.0 `spawn_scoped_mbsync` in `sync_lifecycle.py`
  replaced the 1.0.13 `subprocess.Popen(user=uid, group=gid)` pattern
  with `systemd-run --scope --uid=X`. The D-Bus `manage-units` call
  requires polkit auth that headless NAS installs cannot provide.
- **Fix (committed `c67411a`, deployed on both hosts):** reverted
  `spawn_scoped_mbsync` to spawn mbsync directly via `subprocess.Popen(
  argv, user=uid, group=gid, cwd=cwd, env=env, start_new_session=True)`
  — identical mechanism to `mail_batcher.run_batched_sync`. Ambient
  CAP_SETUID/SETGID on the service unit makes it work. Cancel via
  scope-unit → cancel via `os.killpg(pgid, SIGTERM)` (admin.py's
  existing batcher-mode fallback becomes the only path).
- **Verification:** WebUI Sync-now for Shreya on pnas-omv5s progressed
  past the polkit failure → mbsync got launched, connected to Gmail
  imap.gmail.com:993, entered SASL negotiation. See Layer 2.

### Layer 2 — generate_mbsyncrc emits nothing for AuthMechs (FIXED in 1.1.2)

- **Symptom (post-Layer-1):** vaman's mbsync assertion-crashed at
  `drv_imap.c:2033 imap_free_store: !ctx->pending && !ctx->in_progress`
  after `Authenticating with SASL mechanism XOAUTH2 / Error: IMAP wants
  more steps despite successful SASL authentication`. Shreya's mbsync
  hung idle-with-ESTABLISHED-connection for 9+ min at the same SASL
  step, no crash, just wedged. Both accounts use `auth_type:
  app_password` in `accounts.json`.
- **Root cause:** `generate_mbsyncrc` (app.py:318) had no `AuthMechs`
  emit for the non-oauth2 branch. mbsync 1.5.x then auto-picks the
  strongest SASL mechanism the server advertises. Newer Gmail accounts
  (Shreya, vaman) have Google IMAP advertising `XOAUTH2` first; mbsync
  tries XOAUTH2 and hands over the app-password as if it were an OAuth
  bearer token; Gmail asks for continuation prompts that never come;
  mbsync either hangs or asserts.
- **The tell:** madhav's `mrcolonel@gmail.com` (also `auth_type:
  app_password`, also gmail, same host as Shreya) syncs fine — because
  Google's advertised SASL order for that grandfathered account puts
  `LOGIN`/`PLAIN` ahead of `XOAUTH2`, so mbsync unaided picks LOGIN and
  it works.
- **Fix (committed `775c6b0`, deployed on both hosts):** in the
  non-oauth2 branch of `generate_mbsyncrc`, added
  `lines.append('AuthMechs LOGIN')`. Forces mbsync to skip XOAUTH2
  entirely. LOGIN + TLS (SSLType IMAPS) is safe — password transits
  inside the SSL/TLS tunnel. Works across Gmail, iCloud, Fastmail,
  generic IMAP.
- **Post-fix state:**
  - Both hosts' regenerated `.mbsyncrc` now have `AuthMechs LOGIN` in
    the IMAPAccount block. Confirmed with:
    - `awk '/^IMAPAccount/,/^$/' /datapool/homes/homes/Shreya/.mbsyncrc`
    - `awk '/^IMAPAccount/,/^$/' /srv/dev-disk-by-uuid-a6cb3426-a3e3-4439-91c1-cac1acf9d708/homes/vaman/.mbsyncrc`
  - Retest via WebUI Sync-now → mbsync reached `AUTHENTICATE LOGIN` step
    to Gmail. See Layer 3.

### Layer 3 — mail-archiver-cred returns empty/raw-encrypted (DIAGNOSED, NOT FIXED)

- **Symptom (post-Layer-2):** Shreya's WebUI `Sync failed: Authentication
  failed. Check that the email address is spelled correctly... IMAP
  command 'LOGIN ' returned an error: NO [AUTHENTICATIONFAILED] Invalid
  credentials (Failure)`. vaman's WebUI `Sync failed: TLS/SSL error
  connecting to mail server. The server certificate may have changed.
  IMAP command 'LOGIN ' returned an error: Empty username or password.`
  Note the `LOGIN ` with trailing space — both user + pass were empty
  (vaman) or wrong (Shreya).
- **Root cause diagnosis (proven):**
  1. `.pass` files are mode 600 owned by the target user (Shreya:users,
     vaman:users), 44 bytes of base64-encoded encrypted content.
  2. `.secret_key` is `/opt/mail-archiver/.secret_key` mode 640
     `root:mail-archiver`.
  3. At runtime, `mail_batcher` / `spawn_scoped_mbsync` calls
     `subprocess.Popen(user=1004, group=100, ...)` to launch mbsync as
     Shreya/vaman. Python's `user=`/`group=` params set EUID + EGID but
     **do NOT set supplementary groups**. So the mbsync child process
     runs with supp-groups only [100] (users' primary gid), NOT with
     [100, 987/mail-archiver] which Shreya's `id` shows.
  4. mbsync's PassCmd fires `/usr/libexec/mail-archiver-cred Shreya
     shreyadiwan0@gmail.com`. That helper imports app and calls
     `load_credential`, which:
     - Reads the .pass file → gets 44-char base64 (Shreya CAN read her
       own file).
     - Calls `_get_encryption_key()` → accesses `app.secret_key` which
       is read from `/opt/mail-archiver/.secret_key`. **Shreya's mbsync
       child does NOT have the mail-archiver group → cannot read
       .secret_key → key derivation fails.**
     - `load_credential` has a try/except at line 515–521. The exception
       is swallowed; the fallback at line 523 returns the raw file
       content as-is → mbsync sees an unparseable "password" and Gmail
       rejects with `Invalid credentials`.
  5. **Different symptom for vaman** because Debian 13 (python 3.13) vs
     Debian 12 (python 3.11) differ in something along the app-import
     path — the entire `from app import load_credential` may fail on
     pnas-omv12s, and the helper returns empty at that point.
- **Empirical confirmations:**
  - `sudo -u Shreya /usr/libexec/mail-archiver-cred Shreya
    shreyadiwan0@gmail.com` → returns
    `<redacted — 44-char encrypted credential blob>` (44 chars, the raw
    encrypted content) — sudo DOES preserve supplementary groups so
    this test works even when the real runtime path doesn't. So the
    encryption-key derivation itself is separately broken (not shown
    yet how) OR sudo actually doesn't hit the group problem but hits
    the same fallback-to-raw path via a different route.
  - `sudo -u vaman /usr/libexec/mail-archiver-cred vaman
    vaman.diwan@gmail.com` → returns EMPTY (0 chars).
  - `sudo -u Shreya python3 -c "from app import load_credential;
    print(load_credential('Shreya', 'shreyadiwan0@gmail.com'))"` with
    proper env vars set → returned len 16 (correctly decrypted 16-char
    Gmail app-password).
  - So there is inconsistency between how the helper invokes
    load_credential and how a direct python -c invocation does.
    Something about the helper's environment or module-import path
    triggers the exception fallback.
- **madhav's mrcolonel@gmail.com works** via mail_batcher's periodic
  cron-driven sync (hourly via `/etc/cron.d/mail-archiver` — see
  `deploy.sh` for the exact cron line). Whether it works because
  mail_batcher runs under gunicorn (which HAS mail-archiver group even
  after setuid drop, via Ambient caps + service unit context), or for
  some other reason, is not yet confirmed. Do NOT assume the batcher is
  free of the same bug until proven.

### Layer 3 — proposed code fix (unimplemented)

Two orthogonal changes that together would close this:

**(a) Add `extra_groups` to Popen calls** — pass the user's full
supplementary-group list into `subprocess.Popen(user=uid, group=gid,
extra_groups=[...], ...)`. Sample:

```python
import grp, pwd
pw = pwd.getpwuid(uid)
supp = [g.gr_gid for g in grp.getgrall() if pw.pw_name in g.gr_mem]
kw['extra_groups'] = supp
```

Apply in **both** `sync_lifecycle.spawn_scoped_mbsync` **and**
`mail_batcher.run_batched_sync` (and any other Popen(user=) callsite).

**(b) Separately debug why mail-archiver-cred hits the raw-content
fallback** even when invoked via sudo -u Shreya (which does preserve
mail-archiver supp-group). Instrument the try/except at app.py:515–521
to log what exception it swallows. Likely a Flask app-context or
secret_key initialization issue when app.py is imported as a non-Flask
module (fresh Python interpreter, no Flask lifecycle). May need a
dedicated key-derivation entry point that doesn't require Flask
runtime state.
